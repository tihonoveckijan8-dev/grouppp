# BandPlan UI audit — 2026-10-09

## Scope and safety constraints

This audit is based on the current `main` source and existing GitHub Actions Playwright smoke-test output. It is not a claim that every screen/theme/viewport has been manually inspected. No application runtime code is changed by this document.

Protected behavior for the redesign:
- Do not change Supabase/auth/data logic, route/hash semantics, localStorage key formats, or service-worker behavior as part of visual-only changes.
- Do not delete existing features.
- Every implementation stage must be isolated, tested, and committed before proceeding.
- If a test fails, stop and repair/revert that stage before continuing.

## Initial findings

### P0 — Design-token consolidation risk
`bandplan.css` is a very large stylesheet (~339 KB). It contains theme tokens, accent presets, and a generated `--raw-color-001` … `--raw-color-223` compatibility block. Removing these colors or replacing all color literals in one pass would risk breaking component, print, scene, and legacy styling. First inventory usage; migrate only small, verifiable batches.

### P1 — Theme and accent contrast is not fully verified
The stylesheet defines light, dark, and AMOLED tokens and preset accent colors. `index.html` initializes a stored theme/accent before app startup. The current existing smoke test does not prove all text/background and UI/background contrast pairs meet WCAG thresholds across all themes and accents. Add contrast tests against rendered token pairs before changing tokens. Keep legacy saved accent values working.

### P1 — Responsive visual coverage is incomplete
Existing smoke logs report no horizontal overflow in the tested auth gate at widths from 320 to 3440 px. That is useful but does not establish layout correctness for calendar, song detail, setlist detail, settings, event form, or scene mode. Extend browser coverage by screen and viewport before changing shared layout rules.

### P1 — Component and form defects need targeted reproduction
User-reported issues to verify with browser screenshots:
- event participant labels overlap;
- data deletion button text is clipped;
- song titles, lyrics, song parameter values, accent menu values, and email values have poor contrast in light theme;
- page headers/actions lack consistent horizontal padding;
- setlist-library search placeholder is not visible;
- AMOLED selected segment, slider, and calendar grid borders are too subtle.

These remain reproduction targets until the corresponding screen is exercised in browser tests.

### P2 — Calendar and card hierarchy
Verify day-cell geometry, today marker, selected-day ring, mobile selected-day event list, clickable card states, and the nearest-event block. Preserve calendar/event behavior and existing card visual identity while adjusting presentation.

### P2 — Component language consistency
Review primary/secondary/tertiary/destructive action hierarchy, switches/radios/segmented controls, chip vs chord vs status badge semantics, icon consistency, radius/spacing scales, and duplicate headings. Apply only after screen-specific tests exist.

## Safe implementation plan

1. **Baseline:** keep this audit on an isolated branch; run existing syntax/build/smoke tests and record the result.
2. **Test scaffolding only:** add a deterministic color-contrast test for explicit theme/token pairs and a rendered overflow/screenshot matrix. Do not change runtime logic.
3. **Targeted layout fixes:** address clipping/overlap and page gutters in the smallest CSS scope possible. Capture before/after screenshots and run smoke tests.
4. **Theme readability:** fix verified text/control contrast violations using existing tokens first; add focused regression assertions.
5. **Accent coverage:** inventory accent usages, then migrate a small group at a time. Preserve current settings/localStorage representation and test legacy values such as `red`.
6. **Component semantics:** improve switches, badges, actions, and card interaction affordances without changing handlers or routes.
7. **Responsive review:** validate the required screens at 360×800, 390×844, 768×1024, 1280×800, and 1920×1080 in light/dark/AMOLED, with red/blue/amber accents.
8. **Final verification:** existing tests + contrast checks + source color scan + overflow/overlap checks + screenshot review. Stop on the first failure; do not merge an unverified stage.
